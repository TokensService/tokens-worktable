# 流水线任务并行执行设计

日期：2026-09-11
状态：已确认

## 背景与目标

当前流水线支持不同目标机器上的多个流水线运行并行，但单次运行内部仍按任务顺序串行推进。此次改动为单次流水线增加显式任务并行能力，并让页面手动运行、API 运行和定时运行保持一致。

目标如下：

- 用户可在流水线编辑器中把连续普通任务声明为并行组。
- 编排区直接绘制任务的分叉、并行执行和汇合关系。
- 并行任务分别显示状态、进度、耗时和阶段详情日志。
- 任一阻断型任务失败时，取消组内仍在执行的任务并终止流水线。
- 页面、API 和定时任务使用相同的分组、变量、失败与归档语义。
- 旧流水线配置保持原有串行行为。

本次不增加命名并行组、跨非连续任务分组、并行度上限或 DAG 依赖表达式。

## 配置模型与分组规则

普通阶段增加可选布尔字段：

```json
{
  "id": "unit-test",
  "name": "单元测试",
  "parallel": true
}
```

- 只有 `parallel === true` 才表示并行；字段缺失、`false` 或非法值均按串行处理。
- 最大连续的 `parallel: true` 普通任务构成一个并行组。
- 未标记任务独立构成串行执行单元。
- 系统预设任务不能标记并行，并天然切断前后并行组。
- 只有一个任务的并行组按普通单任务执行，但仍保留 `⚡` 标识，方便用户发现配置。
- 复制、草稿、导入导出、云端持久化、API 计划快照和定时计划快照均保留 `parallel` 字段。
- 现有 API 请求体不变；服务端从已保存流水线的阶段配置中取得该字段。

## 编辑器与编排视图

流水线编辑器的普通任务卡新增“并行执行”复选框。系统预设任务行不展示该开关。只读内置流水线继续沿用现有禁用规则。

编排区不只添加文字标签，而是直接呈现结构：

```text
环境检查 ──┬─ 构建镜像 ─┬── 发布
            ├─ 单元测试 ─┤
            └─ 模型评测 ─┘
```

并行组使用带 `⚡ 并行组` 标题的边框容器、左侧分叉轨和右侧汇合轨。组内每个任务仍是可点击的独立节点，并独立显示运行状态与进度。后续串行节点在全部并行任务成功前保持等待。

拖拽仍只改变阶段顺序。重排后按新的连续标记自动重新计算并行组，不保存额外组 ID。

## 阶段详情与日志

阶段详情采用“选中任务独立打印”：

- 点击某个并行任务后，详情面板只显示该任务的 stdout、stderr、状态、耗时、输入变量和输出变量。
- 多个并行任务的实时输出不会混入同一个控制台。
- 页面继续保留当前的有界实时尾窗和最后 20 行详情策略；完整输出不截断地进入任务归档。
- 每个任务继续写入独立文件 `run-<tag>-NN-任务名.log`，`NN` 始终按原编排顺序编号。
- 汇总日志和 profiling 中的任务顺序按编排顺序记录，而不是按完成先后记录。

## 通用执行语义

页面和服务端都先把阶段序列转换为执行批次。串行任务是单元素批次；并行组是多元素批次。只有当前批次成功结束后才启动下一批次。

并行批次启动时：

1. 对进入批次前的运行变量池创建快照。
2. 每个任务取得独立的变量副本、计时器和取消控制器。
3. 同时启动组内全部任务。
4. 等待全部任务成功，或等待第一个阻断型失败触发组取消。
5. 全组成功时，按编排顺序把各任务的输出变量合并进主变量池，再进入下一批次。

同组任务不能读取彼此输出。若多个任务输出同名变量，编排位置靠后的任务确定最终值。这一规则与完成顺序无关，保证页面、API 和定时运行结果一致。

配置为“不执行”的任务立即进入 `skipped` 终态，不影响同组其他任务。预设任务保持既有阻断规则：环境检查失败会阻断；环境清理和 Profiling 失败不阻断。由于预设任务不进入并行组，其行为不产生组内歧义。

## 失败、中止与重试

- 并行组中任一普通任务失败后，立即发出组级取消信号。
- 已成功或已失败的任务保留真实终态；仍在运行的脚本、HTTP、EvalTokens 或模拟任务尽力取消，并标记为 `aborted`。
- 后续批次保持未运行，整条流水线记为失败。
- 用户中止运行时，取消当前组内所有在途任务，再沿用现有整条运行的中止收尾。
- 页面脚本流、HTTP/EvalTokens 请求和模拟计时器使用任务级取消句柄；服务端脚本进程、fetch/轮询和模拟等待接收统一的取消信号。
- 取消后的迟回结果必须通过运行令牌与任务终态守卫丢弃，不能覆盖失败/中止状态或启动后续任务。
- 从并行组内失败任务重试时，从该并行组第一项重新执行整组。变量池恢复到组入口快照，组内此前成功、失败或中止的结果全部复位，避免使用不完整输出。

## 普罗数据采集

串行任务保持现有逐任务采集规则。并行组只保存一份普罗数据：

1. 并行组执行期间只记录各任务自己的开始与结束时间，不立即发起采集。
2. 组结束后，从勾选“收集普罗数据”且进入 `success` 或 `failed` 终态的任务中选择实际运行时间最长的一项。
3. 时长相同时选择编排位置靠前的任务，保证结果稳定。
4. 只按所选任务的“开始时间 → 结束时间”采集一次，继续写入其 `{任务名}-{阶段序号}-普罗数据` 目录。
5. 其他并行任务不重复采集；`skipped`、`aborted` 或用户中止的任务不参与选择。
6. 没有合格候选任务时不采集。采集失败只记录告警，不改变流水线结果。

页面采集继续在后台执行，不阻塞后续任务；服务端在写最终历史和归档前等待该次采集收尾，以保证 API/定时运行产物完整，但采集结果不影响流水线成功或失败。

## 页面执行器

页面增加纯分组辅助函数，供编排渲染、启动、失败重试和测试共同使用。现有各阶段执行函数继续负责具体协议与日志处理，外层协调器负责批次推进。

并行任务使用子运行上下文保存任务级计时器、取消器和变量副本，同时共享父运行的阶段快照与节点状态表。渲染与选中操作解析回父运行，确保用户仍能在一个编排视图中切换任务。父运行维护当前活动子任务集合，供用户中止、失败连带取消和收尾清理使用。

## API 与定时服务端执行器

服务端 `execPlan` 提取单阶段执行函数，并由批次协调器调用：

- 串行批次直接执行一次。
- 并行批次以相同上游变量快照并发执行。
- 单阶段执行返回状态、完整日志、变量增量、持续时间及归档信息，不直接修改共享变量池。
- 协调器按编排顺序合并成功结果、写历史与 profiling。
- 第一个阻断型失败触发共享取消控制器，随后等待各任务完成取消收尾，避免后台进程或请求泄漏。

`runStageScript`、HTTP/EvalTokens 执行器和可取消等待接受外部 `AbortSignal`。旧 API 流水线和旧定时计划没有 `parallel` 字段，因此自然维持串行。

## 归档与历史兼容

- 单次运行仍只产生一条历史记录。
- 任务日志文件、汇总日志、profiling 阶段列表和普罗目录仍使用原阶段序号。
- 并发写入只触及各自唯一的任务日志路径；汇总文件和 profile 仍在批次收尾后单点写入。
- 历史回放继续按阶段 ID/名称加载独立日志，不需要新的回放协议。
- 失败组中已取消任务在历史与 profile 中记录为 `aborted`，后续未启动任务不生成任务日志。

## 验证策略

采用测试驱动实现，至少覆盖：

- `parallel` 编辑、载入、保存、草稿和旧配置兼容。
- 编排区生成分叉/汇合容器，组内节点仍可独立选择详情。
- 两个延迟任务确实重叠运行，后续串行任务等待整个组成功。
- 组内任务读取同一上游快照，输出按编排顺序确定性合并。
- 一个任务失败会取消在途同伴，后续任务不启动，迟回结果不污染状态。
- 用户中止可一次取消组内所有在途任务。
- 失败阶段重试重新执行整个并行组并恢复组入口变量。
- 并行组只为最长的合格任务采集一份普罗数据。
- API 与定时计划通过服务端执行器遵守相同语义。
- 任务日志独立、历史/profile 顺序稳定，旧串行测试不回归。

完成实现后运行针对性测试、完整 `npm test`、语法检查与构建，并在合并到本地 `dev` 后再次运行完整测试。
